# 2026-07-24 — Snes9x → WebAssembly (contrato wasm-gaming)

Port de **Snes9x** (emulador de Super Nintendo / Super Famicom,
https://github.com/snes9xgit/snes9x) a WebAssembly, empaquetado como engine
SDK conforme a [`@wasm-gaming/engine-specs`](https://github.com/wasm-gaming/engine-specs),
igual que geolith-wasm, fbneo-wasm y hermanos.

**Estado: FUNCIONAL de punta a punta.** Super Mario World (`.sfc` de 512KB)
arranca, renderiza pixel-perfect, corre a 60fps (audio-clocked) con sonido,
input de teclado, savestates y persistencia OPFS de la SRAM. Verificado
headless (Node) y en navegador real (Playwright/Chromium), incluida la demo
shell completa.

---

## 1. Arquitectura (modelo geolith, no fbneo)

Snes9x trae varios frontends (`unix/`, `gtk/`, `qt/`, `win32/`, `libretro/`).
Ninguno sirve en navegador, así que **no se compila ninguno**:

- **`shim/s9x_shim.cpp`** implementa los callbacks `S9x*` que el core enlaza
  (de `display.h`, `controls.h`, `fscompat.h`) y expone ABI plano:
  `s9xwasm_setup/load_rom/reset/exec/frame_rgba/input/state_save/...`
- **Sin SDL, sin ASYNCIFY, sin GL emulado.** El SDK JS llama `_s9xwasm_exec()`
  por frame (= un `S9xMainLoop()`), blitea RGBA a canvas 2D y encola audio
  int16 a un `AudioWorklet` (ring buffer).
- **Pacing por audio**: frames solo cuando el buffer baja de ~90ms.
- Lista de fuentes = `SOURCES_CXX` de `libretro/Makefile.common` menos
  `libretro.cpp` y el filtro NTSC. **Cero parches al upstream.**
- Resultado: `snes9x.wasm` = **2.1MB**, build ~3 min, ~1350fps headless en una
  M-series (22× realtime).

### Datos del core que definen el diseño
- Vídeo: `GFX.Screen` es 16-bit con `GFX.Pitch` **const** (1024B) — el core es
  dueño del buffer, el frontend no lo asigna (a diferencia de lo que sugiere
  el port libretro). Compilado con `PIXEL_FORMAT=RGB565` para que la
  conversión a RGBA sea un shift.
- Geometría **dinámica**: `IPPU.RenderedScreenWidth/Height` cambian en
  caliente (256/512 × 224/239/448/478) según hi-res e interlace. El SDK
  re-lee las dimensiones cada frame y recrea el `ImageData` cuando cambian.
- `S9xMainLoop()` termina llamando a `S9xDeinitUpdate(w,h)` — ahí es donde el
  shim convierte el frame. `S9xSyncSpeed()` se deja como no-op: pacea el host.
- Audio: el APU remuestrea a `Settings.SoundPlaybackRate`, así que se le pasa
  directamente el `AudioContext.sampleRate` → **no hay segunda etapa de
  remuestreo en JS**. 1598 int16/frame a 48kHz NTSC, exacto.
- Savestates: `S9xFreezeGameMem`/`S9xUnfreezeGameMem` (sin FS). No hay API de
  tamaño, pero `nulStream` cuenta bytes sin escribir → se mide con un freeze
  previo. ~823KB en SMW.
- SRAM: `Memory.SRAM` + `(1 << (SRAMSize + 3)) * 128` (memmap.cpp:1870).
- Input: `S9xMapButton(MAKE_BUTTON(pad,btn), S9xGetCommandT("Joypad1 A"))` +
  `S9xReportButton` por frame; el shim mantiene máscaras activo-alto por pad.

## 2. Build — dos trampas que costaron tiempo

- **`UNZIP_SUPPORT` debe quedar SIN DEFINIR**, no definido a 0: `stream.h` lo
  comprueba con `#ifdef`, así que `-DUNZIP_SUPPORT=0` igualmente arrastra
  `unzip.h` y rompe la compilación.
- **MEMFS se queda ACTIVO** (nada de `-sFILESYSTEM=0`). Aunque ROM, SRAM y
  estados van por memoria, el core sondea ficheros laterales opcionales
  (MSU-1, cheats, movies). Con el FS apagado esos `fopen()` **tienen éxito
  contra un stub**, y el core se cree que existen: MSU-1 se activaba y
  escupía "Using msu file ./rom.msu" en bucle. Con MEMFS, `fopen` falla
  correctamente y MSU-1 se queda apagado.
- `-sSTACK_SIZE=5242880`: los 64KB por defecto no bastan para `snapshot.cpp`.
- `fscompat.cpp` ya define `S9xGetFilename`/`S9xBasename`; el shim solo debe
  aportar `S9xGetDirectory` y `S9xGetFilenameInc` (si no, símbolos duplicados).

## 3. Bug real encontrado en el SDK (no era del test)

El pacing por audio se colgaba: `audioCtx.state === 'running'` pero el reloj
de audio **congelado** (`currentTime` = 0.011s tras 2s reales) porque el
navegador headless no tiene dispositivo de salida. Con el reloj parado
`consumedFrames` no avanza, el déficit de buffer nunca reaparece y la imagen
se queda helada para siempre — a 0fps.

El fallback existente solo cubría `state !== 'running'`. Añadido
`audioClockAdvancing()`: si `AudioContext.currentTime` no se mueve en 500ms de
reloj de pared, se considera parado y se pasa a pacing wall-clock. Afecta a
navegadores headless, VMs sin tarjeta de sonido y sinks rotos, no solo al test.

**Los motores hermanos comparten este diseño de pacing y probablemente el
mismo agujero** — vale la pena portar el arreglo a geolith/fbneo/jgenesis.

## 4. Tests (repetibles)

- `make smoke` (`node scripts/smoke-test.cjs`) — headless: carga SMW, 600
  frames, valida samples/frame (1598 @48kHz), colores del framebuffer, energía
  de audio y **round-trip de savestate exacto** (0 píxeles de diferencia).
  Ojo: la comparación correcta es frame(N+1) tras save vs frame(N+1) tras
  restore; comparar contra el frame del momento del save solo mide un frame de
  animación. (Requiere el workaround `"type":"module"` — copia a .cjs.)
- Browser (scratchpad, playwright-core + Chromium cacheado de ms-playwright):
  `test.html` importa el SDK, fetch de la ROM,
  `--autoplay-policy=no-user-gesture-required`; verifica 60fps sostenidos,
  savestate roundtrip (823.407 bytes), screenshot PNG, teclado, pause/resume,
  y que la imagen **anima** (29.614 píxeles cambian en 700ms). Y la demo shell
  completa (setInputFiles + Launch) → título de SMW pixel-perfect a 4:3.

## 5. Pendiente / mejoras

- **MSU-1**: compilado pero inerte (no se montan los ficheros laterales).
  Montarlos en MEMFS desde `assets` lo activaría.
- **BS-X / Sufami Turbo / multi-cart**: necesitan `LoadMultiCartMem` + BIOS
  como assets; sin cablear.
- **Ratón, Super Scope, Justifier, Macs Rifle**: masters desactivados en
  `s9xwasm_setup`; solo joypads.
- **Cheats** (`cheats.cpp`) compilado, sin API expuesta.
- **Filtro NTSC** (`filter/snes_ntsc.c`) no compilado.
- `memmap.cpp` imprime `Map_LoROMMap` con `printf` pelado, así que esa línea
  sale por consola pase lo que pase con `options.logLevel` (que solo controla
  `S9xMessage`).
- Multitap declarado (`options.multitap`) pero **no probado** con un juego que
  lo use.
- PAL no probado (la ROM de test es NTSC).
- CI (.github) espejo de los hermanos, **sin validar aún en Actions**.

## Archivos clave
- `scripts/shim/s9x_shim.cpp` — todo el puente C++ (callbacks del core, vídeo
  RGBA, audio, inputs, savestates, SRAM).
- `src/snes9x.sdk.ts` — SDK contrato (AudioWorklet, pacing, OPFS, teclado,
  gamepads, geometría dinámica).
- `scripts/build-snes9x.sh` — build emcc directo, ref pinneada.
- `roms/` — smario-world-USA.sfc para tests locales (gitignored, no publicar).
